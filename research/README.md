# Research workspace

The Benchmark Team's working directory. Published results for readers outside the team are on the
[results page](../benchmarks/results/README.md).

## Two ideas: benchmarks and studies

- A **benchmark** is one test (IFEval, SciCode, ARC-Easy). It gets **one directory, for good**: how to run it, its
  code, and the results of every model ever measured on it. It does not move when priorities change.
- A **study** is one wave of work with one question, usually a set of tasks from the board, for example "can a
  small model match a large one on these 25 benchmarks?". It gets one directory under `studies/` with a README: the
  question, the models, the benchmarks it uses and the state of each, and the conclusion at the end. When the next
  wave of tasks comes, it is a new study; the benchmarks stay where they are.

So a year from now, `studies/` tells what we did and why, in order, and the benchmark directories hold every number.
One exception predates this rule: the 55 benchmarks of the lm-eval study of October 2026 stay inside
[`studies/2026-10-lm-eval-benchmarks/`](studies/2026-10-lm-eval-benchmarks/README.md), frozen with the protocol they
were built for. One of them measured again gets a new home outside that study.

## Where things go

| you are | put it in |
|---|---|
| adding or running a benchmark that generates answers, whatever way the models run (API, our vLLM, a GPU) | `api-benchmarks/<name>/`, step by step in [`api-benchmarks/README.md`](api-benchmarks/README.md) |
| adding a log-likelihood benchmark (answers scored by probability) | the CodeSOTA runner's catalog in the top-level [`benchmarks/`](../benchmarks/README.md), by [its guide](../benchmarks/docs/contributing.md#5-writing-an-integration) |
| starting a new wave of tasks with its own question | `studies/<YYYY-MM>-<short-name>/README.md`, as [`studies/README.md`](studies/README.md) says |
| analysing results of several benchmarks together | the study the analysis belongs to |
| working on Slayer 1B itself (data, training, tokenizer) | `slayer-1b/` |
| writing code that more than one benchmark uses | `common/`, with its test in `tests/test_<name>.py` |
| retiring a document | `archive/`, with a line in [`archive/README.md`](archive/README.md) |

How every model is configured (precision, decoding, repeats, output limit, standard errors) is in the
[evaluation methodology](../benchmarks/docs/methodology.md), the one methodology for new work. How the team works
(tasks, board, PR, review, checks before a PR) is in [`CONTRIBUTING.md`](../CONTRIBUTING.md). A new top-level
directory in `research/` needs a decision in #bench-team first.

## What is here

| directory | holds |
|---|---|
| [`api-benchmarks/`](api-benchmarks/README.md) | every benchmark we run now, one directory each |
| [`studies/`](studies/README.md) | one directory per wave of work, newest last; finished studies are frozen |
| `common/` | code shared by benchmarks, including the Slayer loader and serving code |
| `tools/` | the number gate (`liczby.py`, `sprawdz_raporty.py`, used by every PR) and the scripts of the 2026-10 lm-eval study |
| `results/` | `LICZBY.json` and `LICZBY.md`, every number of the reports, regenerated by the number gate |
| `tests/` | tests without network or weights |
| `slayer-1b/` | work on Slayer 1B itself |
| [`archive/`](archive/README.md) | retired documents |

The 55 benchmarks of the lm-eval study of October and November 2026, with their cards and the full run of 15
benchmarks × 17 models, are in [`studies/2026-10-lm-eval-benchmarks/`](studies/2026-10-lm-eval-benchmarks/README.md).
