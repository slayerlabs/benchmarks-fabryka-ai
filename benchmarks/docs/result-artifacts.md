# Result artifacts and their validation

A benchmark score is only as trustworthy as the evidence behind it. `codesota.results` checks that evidence: a run
directory with a manifest, the per-sample records, and the aggregated results. It reads files only. It does not run
models, call APIs, or rescore outputs.

This is developer tooling in the `codesota` package. It does not change how work in `research/` is submitted:
benchmarks there keep following [`research/METHODOLOGY.md`](../../research/METHODOLOGY.md) (API benchmarks) and
[`research/METODOLOGIA.md`](../../research/METODOLOGIA.md) (the central run, in Polish).

## What a valid run means

Three different things are easy to confuse. The validator establishes the first two, and only the first two:

| level | what it means | checked here |
|---|---|---|
| Structural validity | fields and types are valid; sample records, counts, states, and digests are consistent; `mean` and `micro_mean` aggregates recompute from the samples; artifacts match their checksums | yes |
| Provenance completeness | the identities and settings listed below are recorded rather than unknown | yes, for presence; the validator cannot tell whether a recorded revision is the true one |
| Scientific verification | the benchmark is implemented and scored correctly: official scorer and protocol, dataset integrity, benchmark-specific evidence | no; this is established by review of the integration |

A run can be structurally valid, with complete provenance, and still measure the wrong thing. Report all three
levels separately; the command prints them that way.

## Validate a run

From `benchmarks/`:

```bash
uv run python -m codesota.results path/to/run-dir [path/to/other-run ...]
uv run python -m codesota.results path/to/run-dir --json   # one JSON report per run
```

The exit code is 0 when every run is structurally valid, 1 when any is not, and 2 on a usage error. Each finding has
a stable code, the JSON path, and a sentence, for example
`checksum.mismatch at $.artifacts[0].sha256: samples.jsonl does not match its recorded checksum`. Warnings are
printed but do not make a run invalid.

From Python:

```python
from pathlib import Path
from codesota.results import validate_run, validate_runs

report = validate_run(Path("run-dir"))
report.ok, report.provenance_complete, report.issues, report.warnings
```

The runs in [`tests/fixtures/runs/`](../tests/fixtures/runs/) are synthetic validation data, not model
evaluations: their model, dataset, scorer, and scores are invented. `local-bf16` has every provenance field
recorded; `provider-api` is the same made-up model through an API, with an unknown served revision and one failed
request. They are generated by [`tests/runs.py`](../tests/runs.py).

## A run directory

```
<run-dir>/
├── manifest.json   who ran what, how, on which data, scored by what; checksums; aggregated results
└── samples.jsonl   one record per selected sample
```

The manifest may list more artifacts (logs, effective configuration), each with `path` (relative, with `/`),
`role` (`samples`, `config`, `log`, `other`), `sha256`, and `bytes`. Exactly one artifact has the role `samples`.
The manifest does not list itself; the validator reports its SHA-256 so a table can cite it.

### Aggregated results and the existing contract

`observations` in the manifest follow the repository's results contract, `urn:fabryka-ai:benchmark-results:2`
([`research/common/README.md`](../../research/common/README.md)). The run manifest is a separate file and leaves
that contract unchanged: the contract describes observations and reported metrics, and the manifest describes
execution identity, configuration, provenance, artifacts, and integrity.

The compatibility is with what is available in this repository, not with the contract's full JSON Schema
(`results.schema.json`, kept in the Space and not in this repository). Concretely:

- Observations must have the required fields, states, and units that `research/common/metryki.py` defines and
  checks (`WYMAGANE_OBS`, `STANY`, `bledy_schematu`). A test compares these constants with that file's source.
- A field outside what `metryki.py` writes is reported as a warning (`observation.extra`), not rejected, because the
  full schema may allow it.
- A read-only test checks that every existing `results.json` under `research/results/central-run/` passes the
  observation checks, and that the files are unchanged afterwards.

One observation per metric, so strict and loose accuracy stay separate results. `source_id_digest` is computed as
in `research/common/ewaluuj.py`: the SHA-256 of the selected sample IDs in record order, joined with newlines.
`results_sha256` is the checksum of `samples.jsonl`.

### Manifest fields

| section | fields |
|---|---|
| top level | `format` (`urn:codesota:run-manifest:1`), `run_id` (unique per run), `provenance_claim` (`complete` or `partial`) |
| `analysis` | `kind`: `primary`, or `exploratory` with `derived_from` (another run ID) and `description` |
| `benchmark` | `id`, `definition` (where the benchmark is defined, for example its directory in `research/benchmarks/`) |
| `protocol` | `id`; `dataset` (`repo`, `revision`, `split`, `n_population`); `scorer` (`name`, `version`, `randomness` with `controlled`, `policy`, `limitations`); `output_preprocessing` |
| `model` | `id`, `repo`, `revision`, `weights_sha256` |
| `inference` | `backend` (`name`, `version`), `dtype`, `quantization`, `temperature`, `top_p`, `max_output_tokens`, `context_length`, `chat_template`, `system_prompt`, `thinking`, `batch_size`, `concurrency`, `seed` |
| `execution` | `started_at`, `finished_at` (UTC, ISO 8601), `source_commit`, `environment` |
| `publication` | `outputs` (`included` or `withheld`), `license` |
| `metrics` | per metric: `id`, `sample_key`, `unit`, `higher_is_better`, `aggregation` (`mean`, `micro_mean`, `external`), `kind` (`quality`, `efficiency`) |

**Unknown is written, never guessed.** A value that cannot be established is `{"unknown": "<why>"}`, for example
`{"unknown": "the provider does not expose the served model revision"}`. `null` means "does not apply" (`top_p`
under greedy decoding) and is accepted only where a field allows it. A missing field is an error.

**`provenance_claim: complete`** requires these fields to be recorded and not unknown: model repository and
revision, dataset and its revision, scorer version, backend version, source commit, and start and finish times.
`partial` says some are unknown. The report's `provenance_complete` is computed either way. Neither value says
anything about scientific verification.

**Scorer randomness is declared.** When a scorer has uncontrolled randomness, `controlled` is `false` and
`limitations` says what it means for reproducibility. The validator does not seed or change a scorer: a
deterministic adjustment is a reviewed protocol decision, recorded in the manifest.

**Accuracy and efficiency are different metrics.** Token counts, latency, throughput, and cost are `efficiency`
metrics of their own, never folded into a `quality` result.

**`external` aggregation** is for a value the scorer computes in a way this package does not recompute. Such a
value is recorded but not checked against the samples, and the report lists it under `not_recomputed`.

### Per-sample records

```json
{"sample_id": "1001", "state": "ok", "scores": {"prompt_level_strict_acc": true}, "raw_output": "...", "scored_output": "...", "error": null}
```

- `sample_id` is a non-empty string or an integer, of one type within a run. IDs are compared as text, so `7` and
  `"7"` are duplicates.
- `state` is one of the schema states. Only `ok` samples are scored and count toward `n_scored`.
- A failed, blocked, or unsupported sample has no scores and records its `error`. A failed request is not a wrong
  answer, and a scored sample cannot carry an error.
- With `publication.outputs: included`, every scored sample has `raw_output` (what the model returned) and
  `scored_output` (what the scorer saw). An empty string is a legitimate output; a missing one is an error. With
  `withheld`, neither is stored.
- For a `percent` metric with `mean` or `micro_mean`, per-sample scores are fractions (0-1, or booleans).

## What the validator checks

- Required fields and their types, explicit unknowns, real UTC timestamps with the finish not before the start.
- Sample IDs are unique and of one type; the number of records equals `n_selected`; `n_population` equals the
  dataset's.
- Sample states are consistent with their scores, errors, and outputs.
- Every declared metric has exactly one observation, and every observation a valid metric definition.
- For an `ok` observation: `n_scored`, `source_id_digest`, and `results_sha256` match the samples, and a `mean` or
  `micro_mean` value recomputes from them. A `percent` value lies in 0-100, and a `ci95` contains the value.
- A non-`ok` observation has no value, and no sample carries a score for its metric.
- Every listed artifact exists inside the run directory and matches its checksum and size.
- Across several runs: run IDs are unique and no directory is listed twice. One protocol ID is not reused for the
  same model with a different protocol fingerprint, which covers the benchmark, protocol (dataset, scorer,
  randomness policy, preprocessing), model, inference settings, and metric definitions. Byte-identical samples in
  two runs give a warning: a copy relabelled as another run cannot be told apart from a fully deterministic rerun.

## Out of scope

The validator does not rescore outputs with an official scorer, decide whether two protocols are comparable,
compute confidence intervals, check licenses, or verify that recorded revisions are the true ones. It does not run
benchmarks. A comparator that flags protocol differences between runs, and an execution path that writes these
files, are separate pieces of work.
