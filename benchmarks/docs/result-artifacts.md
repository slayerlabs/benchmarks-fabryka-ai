# Result artifacts and their validation

A benchmark score is only as trustworthy as the evidence behind it. `codesota.results` checks that evidence: a run
directory with a manifest, the per-sample records, and the aggregated results. It reads files only. It does not run
models, call APIs, or rescore outputs.

This is developer tooling in the `codesota` package. It does not change how work in `research/` is submitted:
benchmarks there keep following [`research/METHODOLOGY.md`](../../research/METHODOLOGY.md) (API benchmarks) and
[`research/METODOLOGIA.md`](../../research/METODOLOGIA.md) (the central run, in Polish).

## Validate a run

From `benchmarks/`:

```bash
uv run python -m codesota.results path/to/run-dir [path/to/other-run ...]
uv run python -m codesota.results path/to/run-dir --json   # one JSON report per run
```

The exit code is 0 when every run is valid, 1 when any is not, and 2 on a usage error. Each problem is printed with
a stable code, the JSON path, and a sentence, for example
`checksum.mismatch at $.artifacts[0].sha256: samples.jsonl does not match its recorded checksum`.

From Python:

```python
from pathlib import Path
from codesota.results import validate_run, validate_runs

report = validate_run(Path("run-dir"))
report.ok, report.issues, report.counts  # counts: samples per state
```

The synthetic runs in [`tests/fixtures/runs/`](../tests/fixtures/runs/) are complete examples: `local-bf16` is a
verified local run, and `provider-api` is the same model through an API, with an unknown served revision and one
failed request. They are generated by [`tests/runs.py`](../tests/runs.py).

## A run directory

```
<run-dir>/
├── manifest.json   who ran what, how, on which data, scored by what; checksums; aggregated results
└── samples.jsonl   one record per selected sample
```

The manifest may list more artifacts (logs, effective configuration), each with `path` (relative, with `/`),
`role` (`samples`, `config`, `log`, `other`), `sha256`, and `bytes`. Exactly one artifact has the role `samples`.

### Aggregated results reuse the existing contract

`observations` in the manifest are observations of the repository's results schema,
`urn:fabryka-ai:benchmark-results:2` ([`research/common/README.md`](../../research/common/README.md)): the same
required fields, units (`percent` 0-100, `score`, `byte_ppl`), and states (`ok`, `not_run`, `blocked_*`,
`unsupported`, `failed`, `skipped`) as `research/common/metryki.py` writes. One observation per metric, so
strict and loose accuracy stay separate results. `source_id_digest` is computed as in the research pipeline: the
SHA-256 of the scored sample IDs in record order, joined with newlines. `results_sha256` is the checksum of
`samples.jsonl`. The test [`tests/test_existing_results.py`](../tests/test_existing_results.py) checks that every
existing `results.json` under `research/results/central-run/` passes the same observation checks, without changing
those files.

### Manifest fields

| section | fields |
|---|---|
| top level | `format` (`urn:codesota:run-manifest:1`), `run_id` (unique per run), `claim` (`verified`, `unverified`, `exploratory`) |
| `analysis` | `kind`: `primary`, or `exploratory` with `derived_from` (a run ID) and `description` |
| `benchmark` | `id`, `definition` (where the benchmark is defined, for example its directory in `research/benchmarks/`) |
| `protocol` | `id`; `dataset` (`repo`, `revision`, `split`, `n_population`); `scorer` (`name`, `version`, `randomness` with `controlled`, `policy`, `limitations`); `output_preprocessing` |
| `model` | `id`, `repo`, `revision`, `weights_sha256` |
| `inference` | `backend` (`name`, `version`), `dtype`, `quantization`, `temperature`, `top_p`, `max_output_tokens`, `context_length`, `chat_template`, `system_prompt`, `thinking`, `batch_size`, `concurrency`, `seed` |
| `execution` | `started_at`, `finished_at` (UTC), `source_commit`, `environment` |
| `publication` | `outputs` (`included` or `withheld`), `license` |
| `metrics` | per metric: `id`, `sample_key`, `unit`, `higher_is_better`, `aggregation` (`mean`, `micro_mean`, `external`), `kind` (`quality`, `efficiency`) |

**Unknown is written, never guessed.** A value that cannot be established is `{"unknown": "<why>"}`, for example
`{"unknown": "the provider does not expose the served model revision"}`. `null` means "does not apply" (`top_p`
under greedy decoding) and is accepted only where a field allows it. A missing field is an error.

**`verified` needs complete provenance.** A run that claims `verified` must be a primary analysis and must know
the model repository and revision, the dataset and its revision, the scorer version, the backend version, and the
source commit. Other runs may record those as unknown and say so through their claim.

**Scorer randomness is declared.** When a scorer has uncontrolled randomness, `controlled` is `false` and
`limitations` says what it means for reproducibility. The validator does not seed or change a scorer: a
deterministic adjustment is a reviewed protocol decision, recorded in the manifest.

**Accuracy and efficiency are different metrics.** Token counts, latency, throughput, and cost are `efficiency`
metrics of their own, never folded into a `quality` result.

### Per-sample records

```json
{"sample_id": "1001", "state": "ok", "scores": {"prompt_level_strict_acc": true}, "raw_output": "...", "scored_output": "...", "error": null}
```

- `state` is one of the schema states. Only `ok` samples are scored and count toward `n_scored`.
- A failed, blocked, or unsupported sample has no scores and records its `error`. A failed request is not a wrong
  answer, and a scored sample cannot carry an error.
- `raw_output` is what the model returned and `scored_output` what the scorer saw, when `publication.outputs` is
  `included`; with `withheld`, neither is stored.

## What the validator checks

- Required fields and their types, explicit unknowns, valid claims and analysis kinds.
- Sample IDs are unique; the number of records equals `n_selected`; `n_population` equals the dataset's.
- Sample states are valid and consistent with their scores and errors.
- `n_scored`, `source_id_digest`, and `results_sha256` match the samples.
- `mean` and `micro_mean` metrics are recomputed from the per-sample scores and must equal the recorded value.
- Every listed artifact exists inside the run directory and matches its checksum and size.
- Across several runs: run IDs are unique, and one protocol ID is not reused for the same model with different
  settings, so bf16 and quantized runs, or local and API runs, cannot pass as the same measurement.

## Out of scope

The validator does not rescore outputs with an official scorer, decide whether two protocols are comparable,
compute confidence intervals, or check licenses. It does not run benchmarks. A comparator that flags protocol
differences between runs, and an execution path that writes these files, are separate pieces of work.
